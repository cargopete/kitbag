## [Unreleased]

### Added

- Per-note targeting and an optional fold into instructions for memory notes. A note's own frontmatter may hold `targets` or `disabled_on` (older `only` / `except` accepted, unknown ids warned about and ignored, not both) and `fold_into_instructions: true`; capture never sets them and a re-capture keeps them, and they are stripped from what a tool's memory file receives. A note whose targeting leaves out its own tool is skipped with a reason; targeting never copies a note into another tool's store. A folded note (frontmatter removed) is appended to the instructions kitbag already writes for a target with no memory store, in the same managed block, never to Claude Code, Hermes or Codex, never when redacted or excluded by its targeting, and from a git source only with `--trust-source`. (#141)
- `kitbag undo` now uninstalls the VS Code extensions its apply newly installed. The transaction records the `publisher.extension` ids that `code --install-extension` actually succeeded on (written after the files, so the order is unchanged), and undo runs `code --uninstall-extension` for exactly those, after restoring the files. Extensions you already had, ones whose install failed, ones withheld by `--trust-source` and ones skipped for lack of `code` or confirmation are never recorded, so never uninstalled. With no `code` on `PATH`, or if an uninstall fails, undo says so, leaves the extension installed and still restores the files; an extension you already removed is fine. Transactions from older versions record none. README: dropped the stale workspace `.vscode/settings.json` from the Editor leftovers (#144) (#143)
- The `vscode` editor target now works at project scope: the same allow-listed AI settings are captured from and merged into the project's `.vscode/settings.json` (created if missing), without touching `User/settings.json`, and no extension is listed or installed at project scope (#144)
- Memory capture and apply follow Claude Code's `autoMemoryDirectory` (docs re-read 2026-11-28, code.claude.com/docs/en/memory). The setting is read from the managed policy file, the project's `.claude/settings.local.json` and `settings.json`, and the user's `settings.json` (only to find the directory; those files are not carried), `~/` is expanded, and a value that is neither absolute nor `~/`-prefixed is skipped with a note. `capture --include memory` saves that directory's notes as `memory/claude-code/auto-memory-directory/`; `apply` adds the notes that aren't there to the directory the setting names on the target when it exists, never overwriting a differing note, and never writes into the managed-policy folder. A directory chosen by a repository's project or local settings file is neither read nor written while `permissions.blockReadsOutsideWorkingDirectories` is on, as Claude Code loads and saves no auto memory there. The default `~/.claude/projects/<project>/memory/` layout is unchanged. (#140)
- opencode 2's global `cli.json` (`~/.config/opencode/cli.json`, or `$XDG_CONFIG_HOME/opencode/cli.json`) is carried at user scope, from the docs re-read 2026-11-28. The documented, bounded keys of `theme`, `animations`, `cursor`, `mouse`, `scroll`, `prompt`, `session`, `tabs`, `diffs`, `attention`, `highlights`, `terminal` and `mini` go in the same `[settings.opencode]` table as `model` and `permissions`, but are written to `cli.json` only, and `opencode.json` gets only its own keys. Values are checked against the documented enums and ranges (a spinner id from the docs' list, a short plain `theme.name`). `plugins`, `keybinds`, `leader`, `experimental`, `debug` and `attention.sounds` (file paths) are not carried, and keys kitbag doesn't know stay in the file. A new file gets `$schema` `https://opencode.ai/v2/cli.json`. There is no project-level `cli.json`, so project scope writes none. `session.permissions = autoaccept` is warned about and, from a git source, withheld unless `--allow-risky-settings` or `--trust-source`. (#142)
- `kitbag secrets set NAME [FILE|DIR] --value-file PATH` adds or replaces one variable in an encrypted `secrets.age`, and `kitbag secrets rotate [FILE|DIR]` encrypts the same variables and token stores again to `--new-secrets-passphrase-file` or `--new-secrets-recipient`. The value is read only from `--value-file` (`-` is stdin, one trailing newline dropped), never from the command line, and is never printed; a replaced variable keeps its capture location, and every other variable and token store stays. `set` opens an existing bundle with `--secrets-passphrase-file` or `--secrets-identity` and writes it back with the same passphrase, or to the keys given again with `--secrets-recipient`; a missing bundle is created `0600` (and listed in a profile directory's `.gitignore`). `rotate` needs a new passphrase or new keys (never both, and not the old passphrase again). Both write the ciphertext to a temporary file in the same directory and rename it over the old one, so a refused or failed run leaves the bundle as it was and no plaintext file, backup or sidecar is written; they refuse git-looking paths, have no `--remote` and write no undo record. Tests look for every fake value and passphrase in the profile directory, the state directory and the output after each (#136)
- `kitbag apply --secrets-from` now fills the fields that already get a resolved value because the tool can't read env references (Claude Desktop, Antigravity, Zed, Cline, the Codex fields it can't read from the environment, and Continue's `command`, `cwd`, `url` and headers) from the bundle for the variables it holds, decrypted in memory only; a variable it lacks still comes from the environment, and `--secrets never` still keeps the placeholder. Tools that read env references keep getting references, never a bundle value. Each field is named in a warning and masked in the diff, and the file is written `0600` on Unix. No value reaches the plan, the diff, the output or the state directory: a file that held no bundle value before the apply is backed up as it was, and `kitbag undo` puts that back; a file that already holds one is written outside the undo record (no backup, no entry, said in the plan), and `kitbag undo` leaves it. Such files are remembered by path only (`bundle-files.json` in the state directory), so a later apply without the bundle doesn't back them up either. `--secrets-from` is still refused with a git source and with `--remote`. Leak tests look for the fake values in the plan, the diff, stdout, stderr, the state directory and the profile directory (#137)
- `kitbag secrets commit [FILE|DIR]` is the opt-in way to keep an encrypted `secrets.age` in git; capture still gitignores it and never commits. For a bundle encrypted to age or SSH keys (the recommended mode) it removes kitbag's `.gitignore` line and, in a git repository, stages only `secrets.age` and `.gitignore`, printing the `git commit` to run. A passphrase bundle gets a loud offline-attack warning and is refused without `--allow-passphrase-commit`; plaintext sidecars, non-age files and git URLs are refused. `kitbag doctor` no longer nags about a tracked, age-encrypted `secrets.age` (it warns if that one is passphrase-encrypted) and still fails a tracked file that isn't encrypted (#138)

## [0.1.11] - 2026-11-28

### Added

- Opt-in encrypted secrets bundle, first slice of #9 (follow-ups #136–#139). `kitbag capture --include secrets` (a bare capture never writes the bundle) writes the values it redacts (MCP env, header, argument and URL literals, and a literal OAuth `client_secret` that a bare capture leaves out) only to a sibling `secrets.age`, a map of `${VAR}` name to value encrypted with age, never into `kitbag.toml` or any plaintext file; `kitbag.toml` keeps the `${VAR}` references. It is encrypted to a passphrase (age's scrypt; `--secrets-passphrase-file PATH`, or a terminal prompt, never the command line) or to age or SSH public keys (`--secrets-recipient`, repeatable; age doesn't mix the two), written `0600` on Unix, and listed in a `.gitignore` that capture creates or extends. `kitbag apply --secrets-from PATH` decrypts a local bundle in memory to check it and to say which of the profile's variables it holds, and writes no value into any tool config, plan, diff, log or undo record (tools keep getting `${VAR}` references); it is refused for git sources (which never supply a bundle, and a `secrets.age` in a checkout is ignored) and with `--remote` (which also never copies `secrets.age` to the host). `kitbag secrets list [FILE|DIR]` prints variable names only. `kitbag doctor` fails on a plaintext secrets file in the profile directory (`secrets.json`, `secrets.decrypted`, `.env` ...) or a `secrets.age` that isn't age-encrypted, as it already did for a literal secret in `kitbag.toml`. Dedicated tests look for fake secrets and passphrases in the profile directory, the state (undo) directory, tool configs, stdout and stderr. Left for later (`Part of #9`): resolving values into tools that can't read env vars without reaching the undo record, an OS keychain or helper, `secrets set` / `rotate`, committing the encrypted file, opening a bundle on a `--remote` host. kitbag does not read the OS keychain, shell profiles or undocumented auth files (checked 2026-11-27) (#9)

- MCP OAuth token stores in the encrypted secrets bundle, phase 2 of #18 (other tools' token stores are dated skips). With `kitbag capture --include secrets` (never a bare capture), Gemini CLI's token file, whose path its official MCP docs name (`~/.gemini/mcp-oauth-tokens.json`, checked 2026-11-27), goes into `secrets.age` as an opaque blob tagged with the tool and the server names and URLs from Gemini CLI's config; kitbag never parses, merges, validates or refreshes it. The bundle is format 2 when it holds a token store and format 1 otherwise, and both open. `kitbag apply --secrets-from` writes it back only to that path, only when `gemini-cli` is a target, only when the file is missing or empty (a non-empty one is never overwritten, since no merge schema is documented), and only when no recorded server URL changed in the profile or in Gemini CLI's config; otherwise it says why and lists the servers to sign in to with `/mcp auth <name>`. It is written `0600` on Unix, after the other files and outside the undo transaction, so no token reaches the plan, the diff, the output or the state directory, and `kitbag undo` leaves it. `kitbag secrets list` names the store (tool and path), never its content. `--secrets-from` is still refused with a git source and with `--remote`. Codex, Claude Code, opencode, Amp, Cursor, Hermes, Zed, Copilot and Claude Desktop stay documented skips with the sign-in checklist: their official docs name no token file, name only a store setting (Codex's `mcp_oauth_credentials_store`), describe login credentials rather than MCP tokens (Claude Code), or say not to edit the store (opencode). No keychain is read (#18).

- MCP OAuth client configuration and a sign-in checklist, phase 1 of #18. A remote server in `kitbag.toml` can carry `[mcp_servers.<name>.oauth]` (`client_id`, `client_secret`, `scopes`, `callback_port`, `redirect_uri`, `auth_server_metadata_url`, `authorization_url`, `token_url`, `issuer`, `resource`, `enabled`), captured from and written to each tool's own keys as its official docs name them (read 2026-11-27): Claude Code `oauth.clientId` / `callbackPort` / `scopes` (a space-separated string) / `authServerMetadataUrl`; Gemini CLI `oauth.enabled`, `clientId`, `clientSecret`, `authorizationUrl`, `issuer`, `tokenUrl`, `scopes`, `redirectUri`; opencode `oauth.client_id`, `client_secret`, `scope`, `callback_port`, `redirect_uri`, `auth_server_metadata_url` and `oauth: false`; Codex `oauth.client_id`, `oauth.callback_port`, `scopes`, `oauth_resource`; Cursor `auth.CLIENT_ID` / `CLIENT_SECRET`; Hermes `auth: oauth` with its `oauth` block. Tokens are never touched: no access or refresh token, expiry, token file (`~/.gemini/mcp-oauth-tokens.json`, `$CODEX_HOME/.credentials.json`, Hermes `auth.json` / `mcp-tokens/`) or keychain item is read, written, copied, logged or printed, and kitbag starts no sign-in. A client secret is carried only as an env reference (`${VAR}`, in each tool's own spelling where its docs have one, never with a fallback value): a literal one in a tool's config is left out of the profile with a warning (never showing it; the encrypted bundle, #9, may carry it later), a literal in `kitbag.toml` is refused, and it is not written to Claude Code (docs: keychain or credentials file) or Codex (stored as plain text, no env reference documented). OAuth settings are not written onto an entry whose URL changed (its old `oauth` goes, as before, and the plan warns), settings the user keeps beside ours (Gemini `audiences`, Hermes `redirect_port`, timeouts) stay while the URL is unchanged, and capturing one server from two tools merges the OAuth settings each names instead of reporting a difference. `plan`, `diff` and `apply` list the servers that still need a sign-in with the tool's own documented command (`claude mcp login <name>`, `/mcp auth <name>`, `opencode mcp auth <name>`, `codex mcp login <name>`, `hermes mcp login <name>`): servers with OAuth settings, and on opencode remote servers without header credentials (its docs: OAuth unless `oauth: false`), never local servers. Dated skips: GitHub Copilot's docs still name none of `oauthClientId`, `oauthScopes`, `oauthPublicClient`, `oauthGrantType` (kept as Copilot-specific), Zed has an in-app prompt and no keys, Amp has no `oauth` keys in `amp.mcpServers` (its `amp mcp oauth login` takes flags, so no checklist line), Claude Desktop names none, and Cursor's docs name no sign-in command. Phase 2, opt-in tokens for the same tool only, waits for #9 (#18)

- `kitbag apply <profile> --remote user@host` and `kitbag diff <profile> --remote user@host` run a profile on another machine over SSH, for SSH remote-development boxes, cloud VMs and anything else whose home has none of your setup (copy, run there, plan shown here, confirm, undo on the host; mapping a project's path into a devcontainer or remote-development workspace is not part of this). kitbag shells out to your own `ssh` with none of its own options, so your ssh config, agent and known-hosts checks decide everything; it copies the profile (without `.git`, `.env*` files and symlinks) into a private temporary directory on the host, runs the host's kitbag there (`--remote-kitbag PATH`, else `kitbag` on its PATH, `~/.local/bin` or `~/.cargo/bin`), shows its plan and diff here, asks before applying unless `--yes`, and removes the copy. The apply is recorded in the host's own state directory, so `kitbag undo` on the host reverts it; `diff --remote --exit-code` passes the host's exit status on. Only `${VAR}` references are sent, never values: a profile holding what looks like a literal secret is refused before anything is sent, and there is no option to send values (the encrypted bundle stays with #9). `--remote-download` (opt-in) downloads this version's release for the host's OS and CPU, the same `kitbag-<target>.tar.gz` and `.sha256` as `install.sh`, and unpacks and runs it only after the SHA-256 matches; without it a host with no kitbag is an error. Local profile directories at user scope only, not git URLs (the host would trust them as local), not on Windows (#34)

- `--no-overwrite` now also keeps existing managed instruction blocks and existing skill support files, and reports each one it kept. A profile that no longer has instructions still removes the old managed block (#38).
- Capture matched secrets it redacted to MCP servers by location, so a server whose name contains a dot (`a.b`) also had its secrets counted under server `a`: they were listed twice and could raise a false "different secret values" warning. Each redaction now records its server (#53).
- A JSON config where a key kitbag edits appears twice (two `mcpServers`, two servers with the name of one kitbag writes, a `command` key twice inside such a server, a setting kitbag writes twice) is refused with an error naming the file and the key. kitbag used to edit the first copy while the tools read the last, so `diff --exit-code` reported no change. Duplicates kitbag doesn't edit, such as a top-level `theme` twice or a key twice in another server, are left alone (#38).
- Edits to JSON and TOML configs and to managed blocks in instruction files keep a file's Windows (`\r\n`) line endings. They used to write the lines they added with `\n`. A file is taken to use `\r\n` when most of its line breaks are `\r\n`; its other lines are then written with `\r\n` too (#38).
- Rules, commands, skills and skill files named after a Windows device (`CON`, `nul.md`, `COM1`, `aux.sh` ...), or whose names differ only in case (`Build.md` and `build.md`), are refused when a profile is loaded or captured, on every OS, naming each one: profiles move between machines, and such files can't be created on Windows or are one file on Windows and macOS (#38).
- Backups of files with very long names no longer fail to be written: the file name part of a backup's name is cut to 100 bytes, without trailing dots or spaces, and the number in front keeps it unique (#38).
- Loading a profile reads at most 64 MiB in all, besides the 2 MiB limit per file; a larger profile is refused with an error naming its directory, and capture refuses to write one (#38).
- The README and `--help` now say where state goes with `--home DIR`: `KITBAG_STATE_DIR` if set, else `DIR/.local/state/kitbag`, never `XDG_STATE_HOME` or `LOCALAPPDATA`. A test covers it (#38).
- A profile `name` with control characters (a newline, tab, escape ..., also at the very end) or invisible text-direction and zero-width characters (U+202A to U+202E, U+2066 to U+2069, U+200B to U+200D, U+FEFF) is refused when the profile is loaded, and `init --name` and `capture --name` refuse one before writing anything. Such a name used to be accepted and stored with each apply in the state directory (#38).
- The README no longer says plain `apply` shows a diff: it lists what it will change and asks; `kitbag diff` and `apply --dry-run` show the full diff (#38).

### Security

- Credentials in a git source URL (`https://user:token@host/...`, `https://<token>@host/...`, `file://user:pass@...`) are passed to `git` and nowhere else: the plan, clone errors (including git's own message), `history`, `undo` and the transaction log show the URL without them. `history` and `undo` also hide them in applies recorded by older versions. An SSH URL keeps its username (#37).
- Git sources over cleartext `http://` or `git://` are refused, as is an `https://` source that git ends up fetching over one (a server redirect or a `url.<base>.insteadOf` rewrite), also when `GIT_ALLOW_PROTOCOL` is set in the environment, unless `--allow-insecure-source` is given (#37).
- `undo` checks every backup against the SHA-256 recorded when it was taken. If one changed since the apply, undo stops before restoring anything, names the file and its backup, and asks for `--force`; with `--force` it restores the backup and warns about it. Applies recorded by older versions carry the same hash and are checked too; an entry without one is restored as before. The hash is stored next to the backups, so it catches a backup that changed on its own, not someone who can write to the state directory (#37).
- Diffs mask private keys that span lines (PEM `-----BEGIN ... PRIVATE KEY-----` blocks) in existing config and instruction files. Each key is shown as one line, `•••••••• (private key, sha256:1a2b3c4d)`, so a changed key still shows up as a change. Diffs and plans also mask whatever capture would redact from text (`export DB_PASSWORD=...`, `Bearer ...`, webhook and query tokens) and, as capture does, a value under a secret-sounding name however short (#37).
- Capture redacts hex-only tokens in URL paths (32 hex digits or more, such as `https://mcp.example.com/u/3f9a.../sse` or a classic 40-digit GitHub token), which the random-looking-segment check missed because it needs upper and lower case. Numeric ids, short ids and SHAs, and full commit SHAs (40 or 64 hex digits) after `commit`, `blob`, `tree` and the like or on `raw.githubusercontent.com` are kept (#37).
- Two different secrets captured under the same name no longer end up behind one `${VAR}`. Within one server (an `API_KEY` in `env` and another in a `docker -e` argument, two passwords in two URLs, two tokens in one command) the second gets a numbered variable such as `${API_KEY_2}`, and the same secret repeated keeps its one variable. Across servers the prefixed name gets a number too when it is already taken. The same server captured from two tools with different secret values is now reported, as a server that differs is (#37).

## [0.1.2] - 2026-11-26

### Added

- `kitbag status [PROFILE]` shows, per tool, whether each managed instructions block and rule file is `in sync`, `tool edited`, `profile changed`, `both changed`, `not applied` or `unsupported` (Cursor user rules live in app storage). Applies now record a hash of each one in the state directory. Without a profile it shows what changed since the last apply. `--exit-code` exits 1 on drift, `--json` prints rows (#32).
- `kitbag sync PROFILE` applies profile changes but leaves a tool whose managed instructions were edited by hand alone, and says so. `--from <target>` pulls that tool's edits back into the profile (redacted like capture, refused if anything still looks like a secret) and applies them to the others, in one undoable transaction; `--overwrite` replaces the edits, with backups. From a git source, `--from` is refused (#32).
- Second-machine sync: capture writes paths under the home directory as `~/...` in MCP server commands, arguments, env values and `cwd` and in Claude Code `permissions`, and apply expands them for the machine it runs on. Re-applying to the original machine changes nothing. `kitbag status PROFILE` also lists MCP servers, commands and skills that were added, changed or exist only in the tool, by name. The README has a "Second machine / dotfiles" section with the recommended flow (#31).

### Security

- `undo --force` no longer follows a symbolic link that appeared or changed after the apply. Each apply records where every file's directory really was; undo leaves a file alone, even with `--force`, when its directory now resolves elsewhere or the file is now a link, reverts the rest and exits with status 1. Applies recorded by 0.1.1 are checked against the recorded path: a symbolic link in it at or below the home directory (or the project directory of a project-scope apply) is refused, while links the system keeps above them, such as `/var` -> `/private/var` on macOS, are fine. `init --force` and `capture --force` replace symbolic links inside the profile directory instead of writing through them, and `init` without `--force` treats a dangling link as an existing file (#35).
- MCP servers from git sources are opt-in. Servers a git profile would add or change are not applied by default; the plan lists each one (command and arguments or URL, env var and header names) under "MCP servers not applied (from a git source)". `--allow-git-mcp NAME[,NAME]` (repeatable) applies the named ones, `--allow-git-mcp` without a value all of them, and `--trust-source` / `--allow-risky-settings` implies it. Servers already in place, and local profiles, are unaffected (#36).

## [0.1.1] - 2026-11-25

### Security

- Profiles from git sources are untrusted by default. They no longer add `permissions.allow` rules (#1), install commands or skills that run shell snippets (``!`cmd` ``, Gemini CLI's `!{cmd}`), or keep `hooks` and `allowed-tools` in skill and command frontmatter (#2). The plan lists what was left out; `--allow-risky-settings` (new alias: `--trust-source`) applies it anyway. `ask` and `deny` rules still apply.
- Local env vars are no longer resolved into MCP servers that a git-sourced profile defines (Claude Desktop, parts of Codex); pass `--secrets resolve` to opt in (#3).
- An MCP server whose command, arguments or URL changes is replaced as a whole, so `npx -y evil-pkg` can no longer inherit the `trust`, `headersHelper`, OAuth or credential keys given to `npx -y good-pkg`. The plan names the dropped keys (#4).
- Capture redacts more secrets: in rule, command and skill frontmatter and in Claude Code permission rules (#5); any value under a secret-sounding name however short, more names (`PGPASSWORD`, `*_PASSPHRASE`, `APITOKEN`, `X-Auth` ...), `${VAR:-literal}` fallbacks and password-only URLs such as `redis://:pass@host` (#6); tokens in URLs wherever they appear, including webhook paths and tokens used as the username (#7); and literal secrets next to a `${VAR}` reference in the same value (#8). `doctor` flags anything left behind.
- With `--project`, every write must resolve inside the real project root, so a symbolic link can't redirect it elsewhere; the apply stops before writing anything. `capture --project` skips, with a warning, project files that link outside the project (such as `~/.aws/credentials`).
- Files that `apply` writes a resolved secret into, from your environment or a `${VAR:-fallback}`, end up mode 0600 on Unix, also when they existed with looser permissions. `undo` puts the old mode back.
- Errors about a broken TOML, JSON or JSONC file give the path, line, column and parser message only. They no longer quote the offending line, which could hold a secret.
- Control characters and bidi overrides in profile or config text are printed as escapes (`\x1b`, `\r`, `\u{202e}`) in diffs, plans, notes, `doctor`, `history` and errors, so a profile can't rewrite or hide lines of the review on a terminal. Files are written unchanged.

### Changed

- `--secrets` defaults to `never` for profiles from git sources (#3).
- Every plan lists each MCP server it adds or changes, with its command and arguments or URL and the names of its env vars and headers (#3).
- The broad-permission warning for local profiles ignores case and extra whitespace, and also names `Bash(*:*)`, whole-file-system `Read`/`Edit`/`Write` rules, interpreters, package runners, containers and piping into a shell (#1). Local profiles also get a warning listing hooks, tool grants and shell snippets (#2).
- A changed argument list, including a version bump such as `pkg` to `pkg@latest`, now counts as a different server: your own keys on that entry (such as `timeout`) are dropped, with a note. Differences in env references alone don't count (#4).

### Fixed

- `doctor` and `apply` flag a `${VAR:-fallback}` whose literal fallback looks like a secret, and diffs mask it (#3).
- A secret written from a `${VAR:-fallback}` is no longer described as "resolved from your environment".
- Permission rules holding `[REDACTED]` markers are not applied back to the tool (#5).

## [0.1.0] - 2026-11-25

### Added

- Portable profile format (`kitbag.toml`, `instructions.md`, `rules/`, `commands/`, `skills/`), format version 1.
- Adapters for Claude Code, Cursor, OpenAI Codex CLI, Gemini CLI and Claude Desktop, at user and project scope.
- `init`, `capture`, `apply`, `diff`, `undo`, `history`, `doctor` and `list-targets` commands.
- Secret redaction on capture, native env-reference rendering on apply, masking in diffs.
- Format-preserving JSON/JSONC and TOML merges, managed blocks in shared markdown files.
- Transactional apply with backups, rollback on failure and undo.
- Profiles from git URLs (`github:owner/repo`, `https://…`, `git@…`, `file://…`).

### Changed

- Profiles from git sources no longer apply settings that let agents act without asking (permissive `defaultMode`, `additionalDirectories`, broad allow rules, Codex `approval_policy = never` / `sandbox_mode = danger-full-access`) unless `--allow-risky-settings` is given. Local profiles are unchanged. `additionalDirectories` and broad rules with arguments such as `Bash(rm -rf *)` are now flagged as risky.

### Fixed

- xAI, Groq, Perplexity, Tavily, Supabase, Replicate, OpenRouter and Firecrawl keys are recognised (free text, env values, headers and args).
- Free-text redaction of URL credentials replaces only the password, instead of swallowing the host and the Markdown after it. Placeholder passwords in documentation examples are left alone.
- Header arguments without a space after the colon (`X-Api-Key:…`, `Authorization:Bearer …`, as in the mcp-remote docs) no longer make capture refuse to write the profile after redacting them.
- Applying a captured profile back to the tool it came from no longer overwrites the original files (or managed blocks) with their redacted copies; files that differ in other ways get a warning about the `[REDACTED]` markers.
- Capture decodes UTF-16 (with a byte-order mark) and drops a UTF-8 byte-order mark in text items; files in other encodings are skipped with a warning instead of aborting the capture.
- A UTF-8 byte-order mark at the start of a JSON/JSONC/TOML config no longer fails with "invalid JSON"; it is kept when the file is written back.
- Capture follows symbolic links inside a skill only when they stay inside the skill. Escaping links, loops, dangling links and unreadable entries are skipped with a warning.
- Capture skips files over the 2 MiB profile limit (and skills beyond 200 files) with a warning, so it no longer writes profiles that `apply` refuses.
- Capture lists Claude Code subagents, output styles and plugins it found but doesn't carry, and drops an `outputStyle` setting that names a custom style.
- Malformed server entries (`"mcpServers": []`, a server that isn't an object) are reported instead of silently ignored.
- `capture` with several tools (`--from all`, `detected` or a list) reports a tool whose config can't be read and captures the rest; it fails only if nothing could be read. A single `--from` still fails loudly.
- `install.sh` and `install.ps1` download `kitbag-<target>.sha256`, the checksum name the release workflow uploads (found in the v0.1.0-rc.1 dry run).
