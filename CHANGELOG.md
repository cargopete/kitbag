## [Unreleased]

### Added

- The `copilot` target is complete for what Copilot's official docs document today: MCP servers, instructions, rules (`*.instructions.md`), project prompt files, skills and custom agents (with legacy chat modes read at capture) at user and project scope, plus hooks. Re-checked against the current VS Code and GitHub Copilot CLI docs, which still match the paths kitbag uses. The README no longer says Copilot CLI reads `.claude/commands/`, which the docs don't say; it says the CLI's docs don't list prompt files. Kept as limits, not gaps: user prompt files and user agents in VS Code's own profile storage (no documented path), prompt files for Copilot CLI, the deprecated `.vscode/mcp.json` (capture only), and Copilot's own MCP and folder trust prompts (#22).
- The `amp` target carries skills, at user and project scope. They are written to `~/.config/agents/skills/<name>/SKILL.md` (where `amp skill add --global` installs; `.config` under `%USERPROFILE%` on Windows, and under `--home`) and `.agents/skills/<name>/SKILL.md` with their bundled files, never to the `.claude/skills` folders Amp also reads. Capture reads Amp's local skill folders in its own order (`~/.config/agents/skills`, `~/.agents/skills`, `~/.config/amp/skills`, `~/.claude/skills`; in a project `.agents/skills`, `.claude/skills`), keeps the first skill of a name and names the one it skipped, and honours `amp.skills.disableClaudeCodeSkills` and `amp.skills.disableGlobalAgentsSkills`. A skill's `mcp.json` and `mcpServers` frontmatter key are neither captured nor written (Amp starts those servers when it finds the skill and documents no approval for them), and kitbag still writes no `amp.mcpTrustedServers` or `amp.mcpPermissions`. Amp removed custom commands in favour of skills, so a profile's commands are written as skills, as Amp's own migration does, and never to a commands folder; a command's arguments template and extra frontmatter are not carried and the plan says so. Amp has no rules directory, so rules are not written (#25)
- New target `amp` for Amp, for MCP servers and instructions, at user and project scope. MCP servers go to `amp.mcpServers` in `~/.config/amp/settings.json` or `settings.jsonc` (`%USERPROFILE%\.config\amp` on Windows) and in a project's `.amp/settings.json` or `settings.jsonc`, edited in place so comments, trailing commas, your other `amp.*` settings, your own servers and keys of yours on an entry (`includeTools`, `oauth` ...) stay: `command`, `args` and `env` for local servers, `url` and `headers` for remote ones. Amp expands `${VAR}` in these values, so references are written as they are and no secret is written to disk. Capture reads one scope at a time, without merging them, and when a workspace and the user settings define the same server the plan says Amp uses the workspace's. Amp asks you to approve a workspace's MCP servers before it runs them (`amp mcp approve`): kitbag never approves one and writes no `amp.mcpTrustedServers` or `amp.mcpPermissions`, and the plan says so. A server that uses `${amp:id-token}` (for Amp orbs) is neither captured nor written. `cwd` is dropped with a warning, a server the profile disables is not written, and an SSE server is written as a plain `url` with a warning, since Amp documents no transport key. Instructions go to `~/.config/amp/AGENTS.md`, and in a project to the file Amp reads, `AGENTS.md`, else `AGENT.md`, else `CLAUDE.md` (shared with the other tools that use the file, so applying several leaves one managed block); capture reads the same file and names the ones Amp ignores, and `~/.config/AGENTS.md`, which Amp also reads, is left alone and named. MCP servers defined on ampcode.com (`amp mcp remote`), servers bundled in a skill's `mcp.json`, skills, permissions, other settings and hooks are not carried, and capture says so (#25).
- New targets `cline` (Cline) and `roo` (Roo Code, also accepted as `roo-code`), for MCP servers and instructions, at user and project scope. Cline: servers go to `mcpServers` in `~/.cline/data/settings/cline_mcp_settings.json` (`CLINE_MCP_SETTINGS_PATH`, `CLINE_DATA_DIR` and `CLINE_DIR` are honoured; user scope only, since Cline documents no project MCP file, and the plan says so): `command`, `args` and `env` for local servers, `url`, `headers` and `type: "streamableHttp"` or `"sse"` for remote ones (capture reads a URL with no `type` as SSE, which is Cline's documented default), `disabled: true` for servers the profile disables, and `autoApprove`, `timeout` and other keys of your own on an entry kept. Cline documents no env-reference syntax, so `${VAR}` is resolved when applied and the file written 0600, or kept as a placeholder with `--secrets never`; `cwd` is dropped with a warning. Nothing else in Cline's data directory is read (it holds the provider settings with API keys), and the older `globalStorage/saoudrizwan.claude-dev` location is not touched. Roo Code: servers go to `mcpServers` in `mcp_settings.json` in the extension's global storage (`.../User/globalStorage/rooveterinaryinc.roo-cline/settings/` under VS Code's user data directory, or VS Code Insiders', VSCodium's or Cursor's when that is where the extension's folder is; Roo's docs give no path, so the file name comes from its source) and, in a project, `.roo/mcp.json`: `command`, `args`, `env` and `cwd` for local servers, `url`, `headers` and the required `type: "streamable-http"` or `"sse"` for remote ones, `disabled`, and Roo's own `alwaysAllow`, `timeout`, `watchPaths` and `disabledTools` kept. References are written as `${env:VAR}`, which Roo expands, so no secret reaches the file; a server with a URL and no `type` is not captured (Roo rejects it), and `roo-cline.customStoragePath` is not read. Both files are edited in place, so comments and your own servers stay. Instructions go in a managed block in `~/.cline/rules/kitbag.md` and `~/.roo/rules/kitbag.md` (each tool reads every file in that directory), and to `AGENTS.md` in a project, shared with Codex, Cursor, Antigravity, opencode, Grok Build, Windsurf and Zed, so applying several leaves one managed block; rules are folded into the block as sections. Rule files you keep yourself (`~/Documents/Cline/Rules/`, `.clinerules/`, `.cline/rules/`, `.roo/rules/`, `.roo/rules-<mode>/`, `.roorules`), workflows, commands, skills, custom modes, hooks and settings are not carried yet, and capture lists the rule files it left (#23).
- New target `continue` for Continue (VS Code and JetBrains), for MCP servers, instructions and, in a project, rules. MCP servers go to `mcpServers` in `~/.continue/config.yaml` (`%USERPROFILE%\.continue\config.yaml` on Windows) and, in a project, to the block files in `.continue/mcpServers/`: a server already defined in a YAML file there is edited in that file, new ones go to `kitbag.yaml` next to them, and one that lives in a JSON file there (the Claude Desktop / Cursor / Cline shape Continue also reads) is captured and left alone on apply, with a note. `command`, `args`, `env` and `cwd` for local servers, `type: sse` or `type: streamable-http` with `url` and `requestOptions.headers` for remote ones. `${VAR}` references in `args` and `env` are written as `${{ secrets.VAR }}`, Continue's documented syntax, which it fills from its own locally stored secrets (kitbag never reads or writes them, and the plan says so), and are read back as `${VAR}`; Continue documents no such syntax for `command`, `cwd`, `url` or headers, so a reference there is resolved at apply time (file written 0600, a project file warned about) or kept with `--secrets never`, and a value you wrote by hand with `${{ secrets.X }}` is kept when it already means the same. The YAML is edited in place: comments, models, prompts and other keys stay, keys kitbag doesn't manage (`connectionTimeout`, other `requestOptions`) are kept, and a layout it can't edit in place (a flow list, tabs) is reported and left alone. A Continue server name with spaces (`Browser search`) is captured as `browser-search` and found again under its own name on apply. Servers the profile disables are not written (Continue has no file flag for it), and Hub blocks (`uses:`) are not captured. Instructions go to a `kitbag-instructions` entry of `rules` in `config.yaml` (plain-text rules there are captured as instructions too and not written twice), and in a project to a managed block in `.continue/rules/kitbag-instructions.md`; Continue's docs don't mention `AGENTS.md`, so it isn't used. Rules are written to `.continue/rules/<name>.md` (`name`, `description`, `globs`, `alwaysApply`) at project scope only, since the docs describe no rules folder in `~/.continue`; `regex` isn't carried. The deprecated `config.json` is never read or written, and kitbag does not create a `config.yaml` next to a `config.json` without one, because Continue would then load only the YAML. Models, context providers, docs and Continue's other stores are not carried yet (#24).
- The `continue` target carries commands as Continue's prompts, at user scope: capture reads the entries of `prompts` in `~/.continue/config.yaml` that are written out there (`name`, `description`, `prompt`) as commands, and apply writes each command as such an entry, the form Continue's reference shows, in place like the other entries: an entry of the same name is replaced (keys of yours on it, like `invokable`, stay), and the others, including Hub prompts (`uses:`), are left alone. A second apply is up to date, `--no-overwrite` keeps an entry that differs, and undo restores the file. Continue's docs describe no prompts folder and no argument placeholder, so a project's `.continue/prompts` is not read or written (capture and apply say so), `$ARGUMENTS` is written as it is with a note, and the argument hint and other command frontmatter are dropped with a note. A prompt kitbag wrote stays when the profile later disables the command for Continue. Continue's docs describe no skills, so none are carried (#24).
- `kitbag status` tracks the `kitbag-instructions` entry of `rules` in Continue's `config.yaml` like the other managed instructions: an edit to it, a change to the profile or both are reported (`tool edited`, `profile changed`, `both changed`), `apply --no-overwrite` leaves an edited entry alone, and `sync --from continue` pulls the edit back into the profile (#24).
- The `cline` and `roo` targets now carry rules, commands and skills, at user and project scope, as files of their own instead of folding rules into the instructions block (so the same rule is no longer applied twice); the instructions block stays in `~/.cline/rules/kitbag.md` / `~/.roo/rules/kitbag.md` and, in a project, `AGENTS.md`, and an older kitbag's folded rules are removed from the user-scope file on apply. Cline: rules in `~/.cline/rules/` and `.cline/rules/` (a rule with globs gets a `paths` frontmatter list; capture also reads `~/Documents/Cline/Rules/`, `~/Cline/Rules/` and `.clinerules/`, and leaves `.cursorrules`, `.windsurfrules` and `AGENTS.md` to their own targets), commands as workflows in `workflows/` (plain markdown; Cline's docs describe the folders but no file format), and skills in `~/.cline/skills/` and `.cline/skills/` (capture also reads `.clinerules/skills/` and `.agents/skills/`, which are never written). Roo Code: plain-markdown rules in `~/.roo/rules/` and `.roo/rules/` (a rule with globs loads always, with a line saying which files it is for, which capture reads back), commands in `~/.roo/commands/` and `.roo/commands/` (`description`, `argument-hint`, `mode`), and skills in `~/.roo/skills/` and `.roo/skills/` (capture also reads `.agents/skills/`). Mode-specific files (`rules-<mode>/`, `.roorules-<mode>`, `.roorules`, `skills-<mode>/`) and Cline's hooks are listed by capture, not read; Roo falls back to `.roorules` only while `.roo/rules/` is empty, so apply warns when its rule files would hide one (#23)
- The YAML editor can edit a block list of mappings with a key (`mcpServers`, `rules`), and writes multi-line text as a block scalar there (#24).

### Changed

- README: the opencode notes now say the target covers everything opencode's docs describe for MCP servers, instructions, rules, commands, skills and agents (checked against opencode.ai/docs on 2026-11-27), name `~/.claude/skills`, `.agents/skills` and `~/.agents/skills` as other places opencode reads skills, and point plugins to #12 and hooks to #13. ## [0.1.8] - 2026-11-27

### Added

- New target `zed` for Zed, for MCP servers and instructions, at user and project scope. MCP servers go to `context_servers` in Zed's `settings.json` (`~/.config/zed` on macOS and Linux, `$XDG_CONFIG_HOME/zed` on Linux when set, `%APPDATA%\Zed` on Windows) and in a project's `.zed/settings.json`, edited in place so comments, trailing commas and your other settings stay: `command`, `args` and `env` for local servers, `url` and `headers` for remote ones, `enabled: false` for servers the profile disables (capture reads it back), and keys of your own on an entry (`timeout`, `oauth` ...) kept. Zed documents no env-reference syntax, so `${VAR}` is resolved when applied and the file is written 0600, or kept as a placeholder with `--secrets never`; a secret written to a project's `.zed/settings.json` is warned about. `cwd` is dropped with a warning and SSE servers are skipped with a note; the plan says Zed starts a project's servers only in a trusted worktree, which kitbag leaves to Zed. Servers from a Zed extension and the older object-form `command` are not captured, with a note. Instructions go to Zed's personal `AGENTS.md` in the config directory, and in a project to the first of `.rules`, `.cursorrules`, `.windsurfrules`, `.clinerules`, `.github/copilot-instructions.md`, `AGENT.md` and `AGENTS.md` that exists, because Zed reads only that one (else to `AGENTS.md`, shared with Codex, Cursor, Antigravity, opencode, Grok Build and Windsurf, so applying several leaves one managed block; `.github/copilot-instructions.md` is shared with Copilot the same way); capture reads that file and names the ones Zed ignores. The Rules Library (stored in Zed's database), rules, commands, skills, agents and settings are not carried (#21).
- New target `hermes` for Hermes Agent (Nous Research), for MCP servers and instructions. MCP servers go to `mcp_servers` in `$HERMES_HOME/config.yaml` (default `~/.hermes`; user scope only, since Hermes documents no project MCP file, and the plan says so): `command`, `args`, `env` and `cwd` for local servers, `url` and `headers` for remote ones, `transport: sse` for SSE servers and `enabled: false` for servers the profile disables. `${VAR}` references are written as they are, which Hermes expands from its environment and `~/.hermes/.env`, so no secret is written to disk. The YAML is edited in place: only the entries kitbag writes change, comments, other settings and your own servers stay as they are, and keys Hermes has that kitbag doesn't manage (`timeout`, `tools`, `auth`, `sampling` ...) are kept; a layout it can't edit in place is reported and left alone. Instructions go to `$HERMES_HOME/SOUL.md` (Hermes has no global AGENTS.md), as a managed block next to what is already there; capture reads only that block, not the persona text around it (a fresh Hermes install seeds one), so it is not carried into the other tools' instructions, and says so. In a project they go to `.hermes.md` / `HERMES.md` when the project has one, since Hermes loads that before `AGENTS.md`, and otherwise to `AGENTS.md`, shared with Codex, Cursor, Antigravity, opencode, Windsurf and Grok Build, so applying several leaves one managed block; the plan warns about an `AGENTS.override.md` that would shadow it. `HERMES_HOME` is honoured. `.env`, `auth.json` and `mcp-tokens/` are never read, captured or written (capture warns when it finds them), and Hermes's skills, memories, sessions and profiles are not carried yet (#28).
- New target `windsurf` for Windsurf (now also shipped as Devin Desktop), for MCP servers and instructions. MCP servers go to `~/.codeium/windsurf/mcp_config.json` (`mcpServers`; user scope only, since Windsurf's docs describe no project MCP file, and the plan says so): `command`, `args` and `env` for local servers, `serverUrl` and `headers` for remote ones (`url` is read too), with `${VAR}` references written as `${env:VAR}`, which Windsurf expands, so no secret is written to disk. Your own keys on an entry (`disabledTools` ...) are kept; `cwd` is dropped with a warning, SSE servers are skipped with a note, and servers the profile disables are not written (capture does read `disabled: true`). Instructions go to `~/.codeium/windsurf/memories/global_rules.md`, or to `AGENTS.md` in a project, shared with Codex, Cursor, Antigravity, opencode and Grok Build, so applying several leaves one managed block; capture also reads the legacy `.windsurfrules`. The plan warns when the instructions are longer than the 6,000 characters Windsurf's docs have allowed `global_rules.md`. Rules, workflows, skills and agents are not carried yet; Devin Desktop's own `.devin/` and `~/.config/devin/` files are not written (#20).
- Rules, commands, skills and agents take the same per-tool targeting as MCP servers: `targets` (an allow-list) or `disabled_on` (a deny-list), and the older `only` / `except`, as frontmatter keys of `rules/<name>.md`, `commands/<name>.md`, `agents/<name>.md` and a skill's `SKILL.md`. Names are checked as for servers: `claude` is read as `claude-code`, a name given twice is kept once, an unknown tool is a warning and ignored, and setting both lists (or a field under both names) or an empty `targets` is an error. The keys are taken out of what is written to a tool, and items without them are loaded, captured and written exactly as before. `apply`, `diff`, `sync` and `status` skip an item for a tool that doesn't get it (`command 'deploy' skipped on codex: disabled in profile (listed in 'disabled_on')`; a folded rule is left out of the tool's rules block), and when kitbag wrote that item's file to the tool earlier, apply removes it in the same undoable transaction. That needs a record: `applied-files.json` in the state directory (new; mode `0600`, kept per scope and project, set aside by `undo`) holds a hash of each rule, command, agent and skill file apply writes, and only a file the same profile and source wrote, and that is unchanged since, is removed (a skill: its recorded files, then its folder if empty). An item added by hand, by another profile or edited stays, and the plan says why; from a git source the removal is listed in the plan, with no extra opt-in. `status` lists an item disabled for a tool that still has it. `capture --force` keeps `targets` / `disabled_on` on the items it captures again, and keeps items with them that no tool had, until `--prune`. Not done yet: mapping to a tool's own disable flags (#33).
- The `claude-code` target carries Claude Code subagents, through the profile's existing `agents/` directory. Capture reads `*.md` files in `~/.claude/agents/` (or `$CLAUDE_CONFIG_DIR/agents/`) and `.claude/agents/`, sub-folders included (flattened to one name as for commands; a clash is an error, and a `README.md` is skipped with a note), and keeps `description` and every other frontmatter key (`name`, `tools`, `disallowedTools`, `model`, `permissionMode`, `skills`, `mcpServers`, `hooks` ...) as it is. Apply writes `<name>.md` into those folders, with a `name` added when the agent has none (Claude Code requires it), so an agent captured from Copilot also works; a second apply is up to date, apply is additive and undo removes only the files kitbag wrote. Keys and values are not translated between tools: apply notes the keys Claude Code's docs don't list and, when writing to Copilot, the Claude Code keys Copilot has no counterpart for. `capture` no longer lists subagents as not carried; output styles and plugins still are. A plugin's `agents/` is still not read (#14).
- Agents with a `permissionMode` that never asks (`acceptEdits`, `auto`, `dontAsk`, `bypassPermissions`) or an `mcpServers` key are warned about in the plan for a local profile and, like agents with `hooks`, `allowed-tools`, `mcp-servers` or a shell snippet, skipped from a git source unless you pass `--trust-source`. A `tools` list alone is not held back (#14).
- The `antigravity` target carries rules and skills, at user and project scope. Rules go to `~/.gemini/config/rules/<name>.md` and `.agents/rules/<name>.md` with the `trigger` Antigravity requires (it discards a rule file without one): `always_on`, `glob` with `globs` as one comma-separated string, `model_decision` for an on-demand rule with a description, and `manual` for one without. Skills go to `~/.gemini/config/skills/<name>/` and `.agents/skills/<name>/` (the directory Codex uses too, so a skill is written once), with `name` and `description` filled in when missing. Capture reads both back, skips a rule file with no valid trigger with a note, and keeps a rule file's version of a rule that is also folded into `GEMINI.md`; a rule only folded there by another tool is still left to that tool's capture. Apply is additive, a second apply is up to date and undo removes only what kitbag wrote. From a git source, a skill with hooks, `allowed-tools` or a shell snippet is held back without `--trust-source`, as for the other tools. The plan warns about a rule file over Antigravity's 24,000-byte limit and a glob with a comma in it, and, when Gemini CLI is a target too, says that Antigravity reads Gemini CLI's folded rules block in `~/.gemini/GEMINI.md` as well, so it sees those rules twice. Workflows (deprecated by Google, with conflicting global paths in its docs), agents, hooks and plugins are not carried (#27).
- Profiles can hold hooks, for Claude Code. They are `[[hooks]]` in `kitbag.toml` in a neutral shape (`event`, `matcher`, `command`, `timeout`, and the tool's other keys such as `args`, `shell`, `async` or `statusMessage` kept in `extra`), with neutral event names (`pre-tool`, `session-start`, `stop` ...) mapped per target, and `claude-code:<Name>` for events only Claude Code has. The scripts they run go in an optional `hooks/` directory, and `{{hooks_dir}}` in a command stands for where they are written, so a profile holds no path of the machine it came from. The manifest version stays `kitbag = 1`; profiles without hooks load and are captured exactly as before. Other targets report hooks and write nothing for them (Cursor and Antigravity have hook files of their own; they are not carried yet). (#13)
- `kitbag capture --include hooks` captures the `command` hooks in Claude Code's `settings.json` (user, or `.claude/settings.json` with `--project`) and copies the scripts they run into `hooks/`, with commands and scripts redacted like other text. `http`, `mcp_tool`, `prompt` and `agent` hooks, unknown events, and scripts outside the Claude config directory (or project) are reported and left out. Without the flag, capture still only notes how many hooks it found; re-capturing into a profile with `--force` keeps its hooks. (#13)
- `kitbag apply --apply-hooks` writes a profile's hooks: the scripts to `~/.claude/hooks/kitbag/` (`.claude/hooks/kitbag/` in a project) and the entries into the `hooks` of `settings.json`, next to the ones you have. It is additive (a profile without hooks removes none), `undo` puts back the settings and removes the script files, and a second apply is up to date. Every plan lists each hook with its command in full and where its script is in the profile; `inspect` and `diff` describe them. A hook whose command or script had a secret redacted at capture is not applied. (#13)
- `kitbag doctor` records a hash of each hook (and script) an apply wrote, in `applied-hooks.json` in the state directory, and reports one that was since edited or removed ("this hook no longer matches what kitbag applied") as a problem. Hooks you added yourself are not checked. (#13)
- The `opencode` target carries rules, commands, skills and agents, at user (`~/.config/opencode/`, or `$XDG_CONFIG_HOME/opencode`) and project (`.opencode/`) scope. opencode has no rule files (its rules are `AGENTS.md`), so rules are folded into `AGENTS.md` as labelled sections, as for Codex, and capture reads them back instead of leaving them behind; with Codex targeted too, the shared block is written once. Commands go to `commands/<name>.md` (`description`, `agent`, `model`, `subagent`/`subtask`), skills to `skills/<name>/` and agents to `agents/<name>.md` (the body is the system prompt). opencode 1's singular `command/`, `skill/` and `agent/` folders are captured too, and written to when they are the ones that exist. Apply is additive, a second apply is up to date and undo removes only the files kitbag wrote. Keys from other tools that opencode doesn't document (`argument-hint`, `allowed-tools`, a `tools` list, `permissionMode`, `hooks`, a `model` that isn't `provider/model`) are left out with a note, not translated. Commands, skills and agents from a git source that run shell commands or hooks still need `--trust-source`. Agents and commands defined in `opencode.json`, opencode 1's `mode/` agents and plugins are not captured, and capture says so (#26).
- Hooks are carried on every tool that documents them, not only Claude Code: `cursor` (`~/.cursor/hooks.json`, `.cursor/hooks.json`), `codex` (`$CODEX_HOME/hooks.json`, `.codex/hooks.json`), `gemini-cli` (`hooks` in `settings.json`), `grok-build` (`hooks/*.json` in `$GROK_HOME` or `.grok/`; apply writes its own `kitbag.json`), `antigravity` (`~/.gemini/config/hooks.json`, `.agents/hooks.json`, as a hook named `kitbag`) and `copilot` (`$COPILOT_HOME/hooks/*.json`, `.github/hooks/*.json`; apply writes its own `kitbag.json`). Capture (`--include hooks`), apply (`--apply-hooks`, plus `--trust-source` from a git source), a second apply being up to date, undo removing only what kitbag wrote, and `doctor` hashes work as for Claude Code, and scripts are copied into `hooks/` and written to a `hooks/kitbag/` directory next to the hook file. Neutral events are mapped to each tool's own names (Cursor `preToolUse`, Gemini CLI `BeforeTool`, Copilot `agentStop` ...); an event only one tool has is `<target>:<Name>` (`cursor:beforeShellExecution`), and one with no documented counterpart is reported, not guessed. Each tool gets only the extra keys its docs list; timeouts are converted (Gemini CLI uses milliseconds, Copilot `timeoutSec`); a matcher is written as it is, with a warning to check it. The tools' own approval steps (Codex's `/hooks` trust, Gemini CLI's warning for unseen project hooks, Grok Build's trusted folders) are not bypassed. In a project Antigravity doesn't document what a hook command runs relative to, so a hook that runs a script is not written there (#13).
- `hermes` carries Hermes Agent's shell hooks, the `hooks:` block of `$HERMES_HOME/config.yaml`, through the same opt-ins as the other tools: `capture --include hooks`, `apply --apply-hooks` (plus `--trust-source` from a git source; `--yes` alone writes nothing), `status` including refused hooks as `not applied`, `doctor` hashes, a second apply being up to date and `undo` removing only what kitbag wrote. User scope only, since Hermes documents no project hook file (the plan says so at project scope). Neutral events map to Hermes's where its docs give the equivalent: `pre-tool` `pre_tool_call`, `post-tool` `post_tool_call`, `prompt-submit` `pre_llm_call` (which the docs name as the counterpart of Claude Code's `UserPromptSubmit`), `session-start` `on_session_start`, `subagent-start` and `subagent-stop`. `session-end` and `post-compact` are not mapped, since the docs don't tie `on_session_finalize` or `post_compaction` to them: those are `hermes:on_session_finalize` and `hermes:post_compaction`, like `hermes:on_session_end` (which fires after every turn) and the rest of Hermes's events (`hermes:<event>`); `session-end`, `post-compact`, `stop`, `post-tool-failure`, `notification`, `permission-request` and `pre-compact` are reported, not guessed. A matcher is written only on `pre_tool_call` and `post_tool_call`, and `fail_closed` is kept. `config.yaml` is edited in place with the YAML editor: only the events a hook is added to are rewritten (comments inside that event's list are lost and your own entries there may be re-quoted), and other events, comments, other keys, `hooks_auto_accept`, MCP servers and your own hooks stay; a layout it can't edit is reported and left alone. The new binary goes to a fresh temporary file in the install directory and is renamed over the old one; `install.sh` used a fixed `kitbag.tmp` name, which followed a link planted there, and `install.ps1` copied over the old exe in place (#37).
- The release workflow pins every action to a full commit SHA, gives each job only the permissions it needs instead of `contents: write` for the whole workflow, and attaches a signed build provenance attestation to each archive (`gh attestation verify kitbag-<target>.tar.gz -R cargopete/kitbag`). CI pins its actions the same way, and checkouts no longer leave the token in the git config. The same workflow attaches `install.sh` and `install.ps1` to each release, so the installer can be pinned to a tag (`https://github.com/cargopete/kitbag/releases/download/vX.Y.Z/install.sh`). The documented `curl | sh` from `main` still works (#37).


## [0.1.3] - 2026-11-26

### Added

- New target `antigravity` for Google Antigravity (app, IDE and CLI), for MCP servers and instructions at user and project scope. Servers go to `~/.gemini/config/mcp_config.json` or `.agents/mcp_config.json`, with `serverUrl` for remote servers and `disabled` for disabled ones; your own keys on an entry (`disabledTools`, `timeoutSeconds` ...) are kept. Antigravity's docs describe no env-reference syntax, so references are resolved at apply time like Claude Desktop (`--secrets never` keeps placeholders) and the file ends up mode 0600; SSE servers are skipped. Instructions go to `~/.gemini/GEMINI.md`, the same file and managed block Gemini CLI uses, so applying to both writes one copy, and to `AGENTS.md` in a project, shared with Codex and Cursor. Capture also reads the other instructions files Antigravity loads. Rules, skills and workflows are not supported yet (#27).
- Per-tool MCP servers: a server in the profile can list the only tools it applies to (`targets = ["claude-code"]`) or the tools it is kept out of (`disabled_on = ["cursor"]`), so one shared profile can keep a heavy server out of the tools that don't need it. Setting both or an empty `targets` is an error. An unknown target name (a typo, or a tool from a newer kitbag) is a warning listing the valid targets and matches no tool, so the profile still loads. `only` and `except` still load as older names, an empty `only` still means no restriction (with a warning), and setting a field under both names is an error naming both; capture writes the new names. `apply`, `diff` and `sync` note each server they skip (`skipped on cursor: disabled in profile`). A server kitbag applied to a tool before and the profile now disables there is removed from it in the same undoable apply, but only when kitbag's records (new `applied-servers.json` in the state directory) show the same profile, by name and source (local directory or git URL), wrote that entry and it is unchanged since; servers added by hand, by another profile or edited are left, and the plan says why. From a git source a removal needs `--allow-git-mcp` or `--trust-source`, like an addition, and is listed as not removed otherwise. `status` shows such servers per tool. `capture --force` into an existing profile keeps `targets` / `disabled_on` (#33).

### Changed

- `kitbag sync PROFILE` holds back only the managed instructions block or rule file that was edited by hand, not the whole tool: one edit to `~/.claude/CLAUDE.md` no longer keeps new MCP servers, rules, commands and skills from reaching Claude Code. Everything else is applied in the same undoable transaction, the plan lists each held-back item (`Skipped: claude-code instructions`) with the `--from <target>` / `--overwrite` hint, and sync still exits with status 1 when it held anything back. A held-back item keeps its old record, so `status` still shows it as edited. `--from` and `--overwrite` work as before (#43).

### Fixed

- A bare `--allow-git-mcp` placed before the source (`kitbag apply --allow-git-mcp github:me/profile`) no longer takes the source as a server name; it means "allow all". A value that looks like a path or URL, or names a profile directory (one with a `kitbag.toml`), is treated as the source. `--allow-git-mcp NAME[,NAME]` and `--allow-git-mcp=NAME` work as before. (#41)
- `apply` and `sync` no longer say "up to date" about a target they skipped; they print `Skipped: <targets>` and the notes say why. With `--no-overwrite`, an apply that kept existing items says "Nothing written; kept N existing item(s)" instead of "up to date" (#38, #42).
- `kitbag undo ""` (or only whitespace) is an error instead of matching any transaction (#38).
- `doctor --to <target>` only checks that target and rejects unknown ones like `apply --to` does, before printing anything (#38).
- Skill scripts keep their executable bit through capture, the profile and apply on Unix. From a git source the bit is only kept with `--trust-source`, and the plan says so otherwise (#38).
- Capturing commands or rules whose nested paths flatten to the same name (`team-build.md` and `team/build.md`) now fails naming both files, instead of silently keeping one (#38).
- `capture --force` into a profile with `.mdc` rules no longer fails looking for a `.md` file (#38).
- `--no-overwrite` now also keeps existing managed instruction blocks and existing skill support files, and reports each one it kept. A profile that no longer has instructions still removes the old managed block (#38).
- Capture matched secrets it redacted to MCP servers by location, so a server whose name contains a dot (`a.b`) also had its secrets counted under server `a`: they were listed twice and could raise a false "different secret values" warning. Each redaction now records its server (#53).
- A JSON config where a key kitbag edits appears twice (two `mcpServers`, two servers with the name of one kitbag writes, a `command` key twice inside such a server, a setting kitbag writes twice) is refused with an error naming the file and the key. kitbag used to edit the first copy while the tools read the last, so `diff --exit-code` reported no change. Duplicates kitbag doesn't edit, such as a top-level `theme` twice or a key twice in another server, are left alone (#38).
- Edits to JSON and TOML configs and to managed blocks in instruction files keep a file's Windows (`\r\n`) line endings. They used to write the lines they added with `\n`. A file is taken to use `\r\n` when most of its line breaks are `\r\n`; its other lines are then written with `\r\n` too (#38).
- Rules, commands, skills and skill files named after a Windows device (`CON`, `nul.md`, `COM1`, `aux.sh` ...), or whose names differ only in case (`Build.md` and `build.md`), are refused when a profile is loaded or captured, on every OS, naming each one: profiles move between machines, and such files can't be created on Windows or are one file on Windows and macOS (#38).
- Backups of files with very long names no longer fail to be written: the file name part of a backup's name is cut to 100 bytes, without trailing dots or spaces, and the number in front keeps it unique (#38).
- Loading a profile reads at most 64 MiB in all, besides the 2 MiB limit per file; a larger profile is refused with an error naming its directory, and capture refuses to write one (#38).
- The README and `--help` now say where state goes with `--home DIR`: `KITBAG_STATE_DIR` if set, else `DIR/.local/state/kitbag`, never `XDG_STATE_HOME` or `LOCALAPPDATA`. A test covers it (#38).
- A profile `name` with control characters (a newline, tab, escape ..., also at the very end) or invisible text-direction and zero-width characters (U+202A to U+202E, U+2066 to U+2069, U+200B to U+200D, U+FEFF) is refused when the profile is loaded, and `init --name` and `capture --name` refuse one before writing anything. Such a name used to be accepted and stored with each apply in the state directory (#38).
- The README no longer says plain `apply` shows a diff: it lists what it will change and asks; `kitbag diff` and `apply --dry-run` show the full diff (#38).

### Security

- Credentials in a git source URL (`https://user:token@host/...`, `https://<token>@host/...`, `file://user:pass@...`) are passed to `git` and nowhere else: the plan, clone errors (including git's own message), `history`, `undo` and the transaction log show the URL without them. `history` and `undo` also hide them in applies recorded by older versions. An SSH URL keeps its username (#37).
- Git sources over cleartext `http://` or `git://` are refused, as is an `https://` source that git ends up fetching over one (a server redirect or a `url.<base>.insteadOf` rewrite), also when `GIT_ALLOW_PROTOCOL` is set in the environment, unless `--allow-insecure-source` is given (#37).
- `undo` checks every backup against the SHA-256 recorded when it was taken. If one changed since the apply, undo stops before restoring anything, names the file and its backup, and asks for `--force`; with `--force` it restores the backup and warns about it. Applies recorded by older versions carry the same hash and are checked too; an entry without one is restored as before. The hash is stored next to the backups, so it catches a backup that changed on its own, not someone who can write to the state directory (#37).
- Diffs mask private keys that span lines (PEM `-----BEGIN ... PRIVATE KEY-----` blocks) in existing config and instruction files. Each key is shown as one line, `•••••••• (private key, sha256:1a2b3c4d)`, so a changed key still shows up as a change. Diffs and plans also mask whatever capture would redact from text (`export DB_PASSWORD=...`, `Bearer ...`, webhook and query tokens) and, as capture does, a value under a secret-sounding name however short (#37).
- Capture redacts hex-only tokens in URL paths (32 hex digits or more, such as `https://mcp.example.com/u/3f9a.../sse` or a classic 40-digit GitHub token), which the random-looking-segment check missed because it needs upper and lower case. Numeric ids, short ids and SHAs, and full commit SHAs (40 or 64 hex digits) after `commit`, `blob`, `tree` and the like or on `raw.githubusercontent.com` are kept (#37).
- Two different secrets captured under the same name no longer end up behind one `${VAR}`. Within one server (an `API_KEY` in `env` and another in a `docker -e` argument, two passwords in two URLs, two tokens in one command) the second gets a numbered variable such as `${API_KEY_2}`, and the same secret repeated keeps its one variable. Across servers the prefixed name gets a number too when it is already taken. The same server captured from two tools with different secret values is now reported, as a server that differs is (#37).

## [0.1.2] - 2026-11-26

### Added

- `kitbag status [PROFILE]` shows, per tool, whether each managed instructions block and rule file is `in sync`, `tool edited`, `profile changed`, `both changed`, `not applied` or `unsupported` (Cursor user rules live in app storage). Applies now record a hash of each one in the state directory. Without a profile it shows what changed since the last apply. `--exit-code` exits 1 on drift, `--json` prints rows (#32).
- `kitbag sync PROFILE` applies profile changes but leaves a tool whose managed instructions were edited by hand alone, and says so. `--from <target>` pulls that tool's edits back into the profile (redacted like capture, refused if anything still looks like a secret) and applies them to the others, in one undoable transaction; `--overwrite` replaces the edits, with backups. From a git source, `--from` is refused (#32).
- Second-machine sync: capture writes paths under the home directory as `~/...` in MCP server commands, arguments, env values and `cwd` and in Claude Code `permissions`, and apply expands them for the machine it runs on. Re-applying to the original machine changes nothing. `kitbag status PROFILE` also lists MCP servers, commands and skills that were added, changed or exist only in the tool, by name. The README has a "Second machine / dotfiles" section with the recommended flow (#31).

### Security

- `undo --force` no longer follows a symbolic link that appeared or changed after the apply. Each apply records where every file's directory really was; undo leaves a file alone, even with `--force`, when its directory now resolves elsewhere or the file is now a link, reverts the rest and exits with status 1. Applies recorded by 0.1.1 are checked against the recorded path: a symbolic link in it at or below the home directory (or the project directory of a project-scope apply) is refused, while links the system keeps above them, such as `/var` -> `/private/var` on macOS, are fine. `init --force` and `capture --force` replace symbolic links inside the profile directory instead of writing through them, and `init` without `--force` treats a dangling link as an existing file (#35).
- MCP servers from git sources are opt-in. Servers a git profile would add or change are not applied by default; the plan lists each one (command and arguments or URL, env var and header names) under "MCP servers not applied (from a git source)". `--allow-git-mcp NAME[,NAME]` (repeatable) applies the named ones, `--allow-git-mcp` without a value all of them, and `--trust-source` / `--allow-risky-settings` implies it. Servers already in place, and local profiles, are unaffected (#36).

## [0.1.1] - 2026-11-25

### Security

- Profiles from git sources are untrusted by default. They no longer add `permissions.allow` rules (#1), install commands or skills that run shell snippets (``!`cmd` ``, Gemini CLI's `!{cmd}`), or keep `hooks` and `allowed-tools` in skill and command frontmatter (#2). The plan lists what was left out; `--allow-risky-settings` (new alias: `--trust-source`) applies it anyway. `ask` and `deny` rules still apply.
- Local env vars are no longer resolved into MCP servers that a git-sourced profile defines (Claude Desktop, parts of Codex); pass `--secrets resolve` to opt in (#3).
- An MCP server whose command, arguments or URL changes is replaced as a whole, so `npx -y evil-pkg` can no longer inherit the `trust`, `headersHelper`, OAuth or credential keys given to `npx -y good-pkg`. The plan names the dropped keys (#4).
- Capture redacts more secrets: in rule, command and skill frontmatter and in Claude Code permission rules (#5); any value under a secret-sounding name however short, more names (`PGPASSWORD`, `*_PASSPHRASE`, `APITOKEN`, `X-Auth` ...), `${VAR:-literal}` fallbacks and password-only URLs such as `redis://:pass@host` (#6); tokens in URLs wherever they appear, including webhook paths and tokens used as the username (#7); and literal secrets next to a `${VAR}` reference in the same value (#8). `doctor` flags anything left behind.
- With `--project`, every write must resolve inside the real project root, so a symbolic link can't redirect it elsewhere; the apply stops before writing anything. `capture --project` skips, with a warning, project files that link outside the project (such as `~/.aws/credentials`).
- Files that `apply` writes a resolved secret into, from your environment or a `${VAR:-fallback}`, end up mode 0600 on Unix, also when they existed with looser permissions. `undo` puts the old mode back.
- Errors about a broken TOML, JSON or JSONC file give the path, line, column and parser message only. They no longer quote the offending line, which could hold a secret.
- Control characters and bidi overrides in profile or config text are printed as escapes (`\x1b`, `\r`, `\u{202e}`) in diffs, plans, notes, `doctor`, `history` and errors, so a profile can't rewrite or hide lines of the review on a terminal. Files are written unchanged.

### Changed

- `--secrets` defaults to `never` for profiles from git sources (#3).
- Every plan lists each MCP server it adds or changes, with its command and arguments or URL and the names of its env vars and headers (#3).
- The broad-permission warning for local profiles ignores case and extra whitespace, and also names `Bash(*:*)`, whole-file-system `Read`/`Edit`/`Write` rules, interpreters, package runners, containers and piping into a shell (#1). Local profiles also get a warning listing hooks, tool grants and shell snippets (#2).
- A changed argument list, including a version bump such as `pkg` to `pkg@latest`, now counts as a different server: your own keys on that entry (such as `timeout`) are dropped, with a note. Differences in env references alone don't count (#4).

### Fixed

- `doctor` and `apply` flag a `${VAR:-fallback}` whose literal fallback looks like a secret, and diffs mask it (#3).
- A secret written from a `${VAR:-fallback}` is no longer described as "resolved from your environment".
- Permission rules holding `[REDACTED]` markers are not applied back to the tool (#5).

## [0.1.0] - 2026-11-25

### Added

- Portable profile format (`kitbag.toml`, `instructions.md`, `rules/`, `commands/`, `skills/`), format version 1.
- Adapters for Claude Code, Cursor, OpenAI Codex CLI, Gemini CLI and Claude Desktop, at user and project scope.
- `init`, `capture`, `apply`, `diff`, `undo`, `history`, `doctor` and `list-targets` commands.
- Secret redaction on capture, native env-reference rendering on apply, masking in diffs.
- Format-preserving JSON/JSONC and TOML merges, managed blocks in shared markdown files.
- Transactional apply with backups, rollback on failure and undo.
- Profiles from git URLs (`github:owner/repo`, `https://…`, `git@…`, `file://…`).

### Changed

- Profiles from git sources no longer apply settings that let agents act without asking (permissive `defaultMode`, `additionalDirectories`, broad allow rules, Codex `approval_policy = never` / `sandbox_mode = danger-full-access`) unless `--allow-risky-settings` is given. Local profiles are unchanged. `additionalDirectories` and broad rules with arguments such as `Bash(rm -rf *)` are now flagged as risky.

### Fixed

- xAI, Groq, Perplexity, Tavily, Supabase, Replicate, OpenRouter and Firecrawl keys are recognised (free text, env values, headers and args).
- Free-text redaction of URL credentials replaces only the password, instead of swallowing the host and the Markdown after it. Placeholder passwords in documentation examples are left alone.
- Header arguments without a space after the colon (`X-Api-Key:…`, `Authorization:Bearer …`, as in the mcp-remote docs) no longer make capture refuse to write the profile after redacting them.
- Applying a captured profile back to the tool it came from no longer overwrites the original files (or managed blocks) with their redacted copies; files that differ in other ways get a warning about the `[REDACTED]` markers.
- Capture decodes UTF-16 (with a byte-order mark) and drops a UTF-8 byte-order mark in text items; files in other encodings are skipped with a warning instead of aborting the capture.
- A UTF-8 byte-order mark at the start of a JSON/JSONC/TOML config no longer fails with "invalid JSON"; it is kept when the file is written back.
- Capture follows symbolic links inside a skill only when they stay inside the skill. Escaping links, loops, dangling links and unreadable entries are skipped with a warning.
- Capture skips files over the 2 MiB profile limit (and skills beyond 200 files) with a warning, so it no longer writes profiles that `apply` refuses.
- Capture lists Claude Code subagents, output styles and plugins it found but doesn't carry, and drops an `outputStyle` setting that names a custom style.
- Malformed server entries (`"mcpServers": []`, a server that isn't an object) are reported instead of silently ignored.
- `capture` with several tools (`--from all`, `detected` or a list) reports a tool whose config can't be read and captures the rest; it fails only if nothing could be read. A single `--from` still fails loudly.
- `install.sh` and `install.ps1` download `kitbag-<target>.sha256`, the checksum name the release workflow uploads (found in the v0.1.0-rc.1 dry run).
